# Pi Session Analyzer — Requirements

## Goal
Provide a small, local CLI that an agent can use to investigate bash usage and tool-reported failures before changing the user's system. The first milestone is an evidence-backed bash inventory; command-family and failure-reason analysis follow. Preserve broader session and context metrics as later work. Deliver metrics and evidence, not automated judgments of task success.

## Scope
### In Scope
- Read existing local Pi JSONL sessions, including sessions archived in pi-chat.
- First milestone: machine-readable bash call/result inventory, raw error counts, and bounded evidence lookup.
- Next: bash command-family and failure-reason classification with explicit uncertainty.
- Later: general JSON overview and single-session detail, session durations, other tool failures, recorded context sizes, and estimated context composition.
- Source references and data-quality warnings so an agent can investigate findings.
- Save reports through ordinary stdout redirection for later comparison.

### Out of Scope
- Dashboard, HTML reports, database, background service, or live telemetry extension.
- LLM-based analysis, automatic prompt/tool changes, and task-success scoring.
- Automated baseline comparison, change tracking, statistical significance, or causal claims.
- Exact provider tokenization, hidden-reasoning reconstruction, and image-token estimation.
- Exact active working time, tool latency, billing analysis, or deleted-session recovery.

## Requirements
The first slice implements the bash-specific contract in R13 plus the minimum read-only discovery, report envelope, and damaged-log handling needed to make its numbers trustworthy. R3's general commands/filters and R5–R10's broader metrics are later deliverables, not prerequisites for the first slice. Extend the foundation incrementally rather than implementing the whole roadmap at once.

- **R1 — Read-only discovery:** Default to `~/.pi/agent/sessions`, allow an explicit session root, and discover JSONL files recursively, including legacy nested folders. Do not load sessions through APIs that migrate or rewrite them. Do not modify sessions, archives, settings, or credentials; do not make network requests.
- **R2 — Archive inclusion:** Scan session files regardless of pi-chat archive state. Current pi-chat archives are descriptors in `~/.pi/agent/pi-chat/projects.json`; archiving does not move or delete the original file. Archive-status labeling and importing external archive paths are unnecessary for the MVP.
- **R3 — Small CLI contract:** Provide `summary` and `session <path>` commands. Both emit one JSON document to stdout; diagnostics go to stderr. `summary` accepts session-root, project/cwd, and since/until filters. Date bounds are UTC, start-inclusive/end-exclusive, and select sessions by first conversation-message timestamp, not individual entries. Return complete selected sessions. `session` reads one explicit file, including outside the default root. Errors and empty results must be distinguishable.
- **R4 — Stable report envelope:** Include schema version, metric-definition version, generation time, selected filters, source root, coverage counts, and structured warnings. Use deterministic row ordering. Emit null plus a reason for unavailable values, not a misleading zero. Session paths and IDs identify evidence; entry IDs and line numbers identify individual events. Do not include raw prompts, thinking, tool arguments, or output bodies by default.
- **R5 — Session count and duration:** Count distinct session IDs; diagnose duplicate copies and count identical copies once. Conflicting copies must not silently inflate totals or be merged. Forked sessions with different IDs remain separate. Report first/last conversation-message timestamps and elapsed seconds; exclude metadata-only activity from duration. For sessions with no conversation messages, duration is unavailable. Overview includes valid-session count, duration sample count, median and p90, plus a compact row per session. Elapsed span includes idle time and is not active effort.
- **R6 — Failure metrics:** Count assistant tool-call blocks, completed tool results, results with `isError: true`, and calls without results. Match results by tool-call ID and validate duplicate/ambiguous matches. Report counts by tool and failed/completed-result rate; a zero denominator produces null. Count assistant `stopReason: error`, `aborted`, and `length` separately. Do not treat cancellations, output limits, missing results, or every nonzero shell exit as a proven agent failure. A tool's unflagged semantic failures are outside automatic detection. Full-history metrics include abandoned branches; label that scope explicitly.
- **R7 — Recorded context size:** For assistant requests with usable usage, report input-context tokens from `input + cacheRead + cacheWrite`, keeping output tokens separate. Do not use `totalTokens` or summed inputs across requests as context size. Preserve model/provider attribution and treat absent, placeholder, or failed-request usage as unavailable unless valid. Report latest and peak recorded input context with evidence and coverage. Do not invent context-window utilization when the historical model limit is unknown. Also report compaction count and recorded `tokensBefore`, labeled separately from provider usage.
- **R8 — Context composition:** In session detail, estimate context composition immediately before each persisted assistant request. Honor that request's parent path, earlier compactions and retained boundaries, branch summaries, context edits, and system-prompt/tool-declaration updates. A flat transcript sum is not acceptable. Separate user text, assistant text, visible thinking, tool-call names/arguments, tool outputs, system instructions, tool definitions, injected/custom messages, and summaries. Count context-visible direct bash execution separately. Extension memory that cannot be reliably distinguished from other injected text stays in its actual source category; do not guess its origin.
- **R9 — Explicit estimation limits:** Use one documented, versioned text-size estimator consistently across categories. Report estimated category tokens and percentages of the estimable context only, with that denominator stated. Keep provider-reported request size alongside these estimates without forcing them to reconcile or distributing an unexplained residual. Do not count signatures, JSONL metadata, or image base64 as ordinary text tokens. Warn about missing historical system state, images, opaque/redacted thinking, unknown roles, and request-time extension/provider transformations. Stored thinking is not necessarily replayed by every provider: label its contribution as a persisted-context estimate, not exact wire input. Unsupported projections produce unavailable composition, not a fabricated result.
- **R10 — Bounded investigation output:** `summary` contains aggregates and compact session rows, not every request. `session` adds request-size/composition checkpoints, failure references, and the ten largest context contributors at the peak estimated checkpoint, identifying source entries and tool names without dumping their bodies. Recorded and estimated peaks are independently labeled. This should let an agent locate a large read/output or repeated failures in the source file.
- **R11 — Damaged and evolving logs:** A partial final line in an active file must not abort the scan; report it. Report malformed interior lines, unreadable files, unsupported versions, unknown entries, and missing tree links with file/line evidence. Only emit metrics unaffected by damage; otherwise mark them unavailable. Document supported session versions explicitly. Report discovered, parsed, skipped, duplicate, and partially analyzed file counts. Partial reports use a documented nonzero exit status distinct from fatal invocation/read failures.
- **R12 — Verification and baseline:** Use synthetic fixtures, never committed personal transcripts. Tests cover linear and branched sessions, compaction, context edits, system patches, tool matching/failures, missing usage, duplicate sessions, empty files, and truncated/corrupt logs. An end-to-end fixture has independently calculated expected metrics and category percentages. A read-only smoke scan of local sessions must produce schema-valid JSON and disclose coverage; it must not change source files. Document one command to save a baseline and rerun the same filters later. Reports with different metric-definition versions are not automatically comparable.

- **R13 — First-slice bash inventory:** Provide `bash summary --root <sessions-directory>` and `bash calls <session-file>`, emitting JSON. Default root is the usual Pi sessions directory. Summary reports scanned/usable/partial files, distinct sessions, observed bash calls, matched completed calls, tool-reported errors, unmatched calls/results, and failed/completed rate (null for no completions). Match call/result IDs within their session and compatible branch ancestry; duplicate or ambiguous matches produce warnings and do not silently inflate counts. Include namespaced bash tools where recorded; distinguish assistant tool calls from direct user shell executions. Scope is full persisted history, not just the active branch. Identical session copies count once; conflicting copies are diagnosed. Copied history across different fork session IDs is not deduplicated initially: disclose that limitation and do not promise exact agreement with pi-stats. `bash calls` defaults to bounded metadata rows with session/file, entry ID, line number, timestamp, tool-call ID, and outcome; support `--failed`, `--limit`, and `--offset`. Only explicit `--include-content` reveals recorded commands and bounded result excerpts, which may contain secrets and are not guaranteed redacted. No classification, date/project filters, retries, context reconstruction, or shell execution in this slice. Keep discovery/parsing, extraction/matching, reporting, and CLI wiring as small separate modules; prefer plain functions. Verify synthetic successful/failed/unmatched/ambiguous calls, branches, duplicates, namespaced tools, empty input, malformed lines, and a truncated tail. A read-only local smoke scan validates JSON and discloses coverage; source files must remain unchanged.
- **R14 — Bash diagnosis:** In the next slice, group bash calls by command family/purpose and observed failures by likely reason. Retain an unknown/mixed category and rule/version evidence. Do not classify a whole compound command solely by its first word, equate no matches or TDD failures with agent mistakes, or claim retry/correction sequences are certain. Report frequency, failure count/rate, share of all failures, affected sessions, and bounded opt-in examples. Rank potential improvements primarily by recurring avoidable failure volume; report raw flags separately from inferred reasons. Label results as heuristics, not causal findings.

## Assumptions
- Project location: `/Users/manuelselch/.pi/agent/git/github.com/ManuelSelch/pi-session-analyzer/`.
- Planned implementation: TypeScript on Node.js, using plain modules and minimal dependencies. Reuse Pi's pure helpers when later context reconstruction needs them; do not start an agent runtime merely to analyze files. No particular CLI or test library is required.
- Start with the session versions actually present locally. Inspect an aggregate inventory before finalizing supported-version handling; do not silently exclude old logs.
- For the initial estimator, a documented characters-to-tokens heuristic is acceptable. The tool must call this an estimate and preserve its version for future replacement.
- Historical files cannot prove exact model input, task success, user effort, or the causal reason for a failure. The MVP supplies evidence for investigation.

## Implementation Plan
### 1. Read-only Bash Inventory
Description: Deliver only R13's `bash summary` and `bash calls` commands using small TypeScript modules for file reading, matching, aggregation, and CLI wiring. Count raw outcomes without guessing failure causes. Verify hand-calculated fixtures, partial-log warnings, privacy defaults, and a read-only local smoke scan. An agent can save a baseline, identify sessions with failed bash calls, and retrieve bounded evidence. No classifier or context analysis yet.

### 2. Bash Usage and Failure Classification
Description: Build R14 on the inventory: add conservative, versioned command-family and failure-reason rules with unknown/mixed fallbacks. Rank groups by volume and failure contribution, expose bounded evidence on demand, and label suspected retries as inferred. Test common simple and compound commands plus ambiguous cases. Inspect the top three recurring local patterns before proposing specialized tools.

### 3. Bash Baseline Workflow
Description: Add UTC date/project filters with explicit selection semantics and document saving/repeating reports. Validate reproducibility, coverage, stable ordering, and the distinction between raw tool errors and classified reasons. State fork-copy limitations and investigate cross-fork deduplication if it materially affects the baseline. No automated comparison engine; do not imply fewer bash calls alone proves improvement.

### 4. General Session and Failure Metrics
Description: Add the previously planned general `summary` and `session` commands, durations and median/p90, all-tool call/result accounting, assistant stop reasons, recorded peak/latest input context, and compaction counts. Reuse the bash foundation rather than duplicating parsing. Verify unavailable values, filter boundaries, and hand-calculated metrics.

### 5. Estimated Context Attribution
Description: Add request-path context reconstruction and the versioned category estimator to session detail. Support compactions, system/tool state, summaries, edits, and branching for declared supported formats; warn or return unavailable for unsupported cases. Add checkpoint composition and the ten largest contributors. Verify against independently calculated fixtures, including abandoned branches and compacted/edited messages that must not contribute.

### 6. Broader Metrics Validation
Description: Validate general session/context reports end to end against synthetic fixtures and a read-only local smoke scan. Document metric definitions, projection coverage, estimation limits, output privacy, and an agent-oriented investigation workflow. Preserve baseline versioning; no dashboard, database, or automated changes.
