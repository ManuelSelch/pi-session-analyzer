# Jev Episode Classification — Requirements

## Goal
Classify one explicitly selected conversation episode: is the user correcting the agent, clarifying, changing requirements, answering an open question, or initiating an architectural review? When it is a correction, identify the observable issue without claiming its root cause or preventability.

This is a feature-scoped proposal, not implementation approval. Preserve the existing root [requirements](../../REQUIREMENTS.md) as the legacy bash/metrics roadmap; do not relocate or rewrite it. Its offline-only constraint continues to apply to existing commands. This feature proposes a narrowly scoped, explicitly authorized network exception for the new command only.

Automatic episode discovery/boundary selection, session-wide scoring, recurrence analysis, recovery scoring, prevention recommendations, generated explanations, caching, dashboards, and automatic configuration changes are out of scope. Reading a real session and projecting an explicitly selected episode are in scope.

## Requirements
- **R1** — Accept one real Pi session JSONL file plus an explicit start entry ID and user-intervention entry ID. Reuse the existing read-only v2/v3 session parser. Follow parent ancestry from the intervention back to the start, reverse it into conversation order, and include both boundaries. Reject missing/ambiguous IDs, a non-user intervention, an unrelated start, cycles, or broken ancestry within the selected range. Do not include sibling branches or later messages. Episode boundaries are selected explicitly, not detected by the model; choose a start that includes the relevant request and agent behavior.
- **R2** — Build Jev's episode representation internally from the selected native entries, not a separately authored input format. Preserve recorded user/assistant text and relevant tool-call/result evidence, with entry identities and declared projection limitations. Exclude hidden thinking and binary/image data; disclose unsupported blocks rather than silently treating them as complete evidence. Omit the manual review's labels, observations, prevention hypotheses and expected answers. Source paths and source-reference mappings remain local and are not needed in the provider payload. Earlier history outside the range is explicitly omitted; this is not exact historical model-context reconstruction. Reject oversized payloads rather than silently trimming context; document a conservative payload-size limit during implementation. No automatic secret-redaction guarantee: preview the selected real evidence before submission.
- **R3** — Ask two independent Jev Choice questions in one request. The first selects the intervention kind: `correction`, `clarification`, `requirement_change`, `decision_response`, `architecture_review`, or `insufficient_evidence`. Define correction as redirecting prior agent behavior/understanding, not proof of negligence or an ignored instruction. Distinguish changed requirements from a previously stated requirement the agent missed; use insufficient evidence when the supplied context cannot resolve the distinction. Mere words such as “no”, “still” or “revert”, and an agent's apology, are not sufficient grounds for correction.
- **R4** — The second Choice selects the primary observable issue: `abstraction_or_intent_mismatch`, `explicit_constraint_missed`, `unsupported_completion_claim`, `speculative_diagnosis`, `ownership_or_boundary_confusion`, `other`, `insufficient_evidence`, or `not_applicable`. Describe clear boundaries: an explicit-constraint miss requires prior evidence of that constraint; an unsupported completion claim asserts delivery without adequate support; speculative diagnosis concerns unverified causal explanations. Both questions judge the supplied evidence independently, not each other's answers. Preserve both raw answers; expose an effective issue only for a correction, otherwise `not_applicable`. Surface contradictory combinations for review rather than inventing a reconciliation.
- **R5** — Treat transcript contents as evidence, never as instructions to the classifier. Rubric criteria must preserve the pilot's negative cases: explicit removal followed by a request to restore, “no” accepting a recommended option, and an async constraint revised during design. Do not infer a historical rule from current preferences, equate disagreement with avoidable error, or treat later user approval as proof of a diagnosis.
- **R6** — Provide a proposed `episode classify <session.jsonl> --from <entry-id> --at <user-entry-id>` command that previews locally by default, with no API key or network required. Its JSON preview includes selected boundaries, projection warnings, the exact provider request body, model, rubric version, request hash and payload size; it explicitly reveals sensitive evidence for review. Only an explicit `--allow-network` submits that invocation's payload. Preview and submission use the same request builder; changed source content must change the recorded hash. An API key in the environment alone must not trigger a request, and existing bash commands must remain offline.
- **R7** — Submit at most one request per invocation using the TypeSafe API and an explicitly pinned model. Enforce a finite timeout; do not retry or fetch additional evidence automatically. Read the key from `TYPESAFE_API_KEY`, never a command argument or repository file. Do not expose it, request contents, or raw provider error bodies in diagnostics. Invalid input, missing credentials in live mode, timeouts, HTTP failures and invalid responses must fail clearly without fabricated classifications. Do not follow cross-origin redirects with credentials.
- **R8** — Live output is one JSON document with schema/rubric versions, session/range/intervention identity, local source references, projection warnings, source-snapshot/request hashes, requested/returned model IDs, returned labels, full probabilities, confidence, usage and elapsed request time. Validate answer types, option keys, finite values/ranges, probability totals within documented tolerance and selected choices against the maximum probability. Output no raw transcript or generated rationale in live mode. Treat all classifications as hypotheses requiring review; do not introduce an arbitrary automatic-accept threshold in this first version. Preview and live output must be distinguishable. Diagnostics use stderr; document fatal/invocation exit code 1, successful preview/live exit code 0, with uncertainty represented in the JSON rather than as transport failure.
- **R9** — Read only the supplied session file; do not execute transcript commands, load agent extensions, migrate sessions, scan other sessions, modify source files or change instructions. Capture one read snapshot for consistent parsing/provenance; disclose that active files may grow between invocations. Write no report/cache automatically: users can redirect JSON into ignored `reports/`. Automated unit/integration tests use synthetic native-format JSONL fixtures and mocked transport, never credentials, paid calls or committed personal transcripts.
- **R10** — Verify the complete offline/HTTP contract and evaluate semantics separately. Synthetic native-format analogues of correction/control cases must exercise the rubric, branch selection, broken ancestry, repeated text with distinct IDs, projection warnings, payload boundaries, input/output validation, privacy, timeout/failure paths, no-network preview and unchanged offline bash commands. Mocked answers prove plumbing, not Jev accuracy. Also validate end to end using a defined real Pi Chat session and selected episode: inspect its preview, perform one explicitly enabled Jev call, compare the prediction with the manual review, record actual usage/disagreements privately, and verify the source was not modified. User approved real-session validation under Q2; that is not approval for a corpus-wide upload. The pilot episodes remain development examples, not a held-out benchmark. Do not claim calibrated confidence or population accuracy from this sample.

## Assumptions
- User confirmed native real-session input and real-session live validation. Start with explicit entry boundaries to avoid adding automatic episode discovery. The existing private `reports/correction-review.json` identifies development cases and expected interpretations, **not** model input; its labels and interpretations must never be sent as evidence.
- Use the archive-button episode E2 from the local pilot as the first defined real-session case: start entry `8fca4ad9`, intervention entry `c3365bde`. Resolve its private source path locally from the pilot evidence; do not copy that transcript into tracked fixtures. Confirm that the selected ancestry includes the request, agent claim and user correction, and inspect the outgoing preview before the live call.
- Proposed provider: direct TypeSafe `POST /v1/systemone`, pinned `jev-1.14.0`, currently documented in the [model catalogue](https://docs.typesafe.ai/models). Use the documented [Choice contract](https://docs.typesafe.ai/primitives/choice) and [API schema](https://docs.typesafe.ai/api/system-one); confirm availability before any approved live trial.
- Preserve Node 24+, TypeScript, small plain-function modules and the existing test tooling. A direct built-in HTTP client can keep the feature dependency-free; no agent framework or Python runtime is needed.
- Retention is governed by provider terms; lack of training on customer data is not a zero-retention guarantee. User authorized a selected real session for validation, not uploading all sessions. Network submission remains explicit and bounded by R6–R7; no live call is made while updating this plan.

## Implementation Plan
### S1 — Session Episode and Rubric
Description: Reuse native session parsing to select one ancestry-bounded episode, normalize its evidence and build the versioned two-question Jev payload (R1–R5). Verify supported JSONL versions, valid/invalid boundaries, sibling-branch exclusion, missing context, unsupported content, excluded annotations and size rejection using synthetic native-format fixtures. Preview the defined real-session episode locally to verify the real format before adding network access.

### S2 — Preview and Jev Classification
Description: Build on S1 to expose the new preview-first CLI and one-request TypeSafe integration (R6–R9). Verify that preview needs no credentials/network, live mode requires explicit permission, submitted content matches preview, valid probabilities/provenance are preserved, and HTTP/timeout/schema failures cannot produce success. Preserve all existing bash CLI behavior. Use mocked transport only; no paid calls required to complete this slice.

### S3 — Real-Session Validation
Description: Build on S2 to validate the defined real Pi Chat session/episode end to end and add a short usage/evaluation guide (R10). Verify existing tests/typecheck and the synthetic native-format regressions. Inspect the real preview, submit one explicitly enabled Jev request, and record label agreement/disagreement, usage, source integrity and projection coverage privately. If credentials are unavailable, report the live-validation blocker rather than substituting mock results as proof. Keep contract verification separate from semantic findings; do not expand into automatic boundary detection or recommendations.
