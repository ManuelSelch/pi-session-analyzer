# Jev Episode Classification — Requirements

## Goal
Classify one explicitly selected conversation episode: is the user correcting the agent, clarifying, changing requirements, answering an open question, or initiating an architectural review? When it is a correction, identify the observable issue without claiming its root cause or preventability.

Classification is submitted directly when the command runs; there is no separate preview mode or network opt-in flag. Jev (a TypeSafe System One model) is the only model allowed to answer; provider differences are limited to endpoint, credentials and model naming.

This is a feature-scoped proposal, not implementation approval. Preserve the existing root [requirements](../../REQUIREMENTS.md) as the legacy bash/metrics roadmap; do not relocate or rewrite it. Its offline-only constraint continues to apply to existing commands. This feature adds an explicitly requested network call for the new command only.

Automatic episode discovery/boundary selection, session-wide scoring, recurrence analysis, recovery scoring, prevention recommendations, generated explanations, caching, dashboards, and automatic configuration changes are out of scope. Reading a real session and projecting an explicitly selected episode are in scope.

## Requirements
- **R1** — Accept one real Pi session JSONL file plus an explicit start entry ID and user-intervention entry ID. Reuse the existing read-only v2/v3 session parser. Follow parent ancestry from the intervention back to the start, reverse it into conversation order, and include both boundaries. Reject missing/ambiguous IDs, a non-user intervention, an unrelated start, cycles, or broken ancestry within the selected range. Do not include sibling branches or later messages. Episode boundaries are selected explicitly, not detected by the model; choose a start that includes the relevant request and agent behavior.
- **R2** — Build Jev's episode representation internally from the selected native entries, not a separately authored input format. Preserve recorded user/assistant text and relevant tool-call/result evidence, with entry identities and declared projection limitations. Exclude hidden thinking and binary/image data; disclose unsupported blocks rather than silently treating them as complete evidence. Omit the manual review's labels, observations, prevention hypotheses and expected answers. Source paths and source-reference mappings remain local and are not needed in the provider payload. Earlier history outside the range is explicitly omitted; this is not exact historical model-context reconstruction. Reject oversized payloads rather than silently trimming context; document a conservative payload-size limit during implementation. There is no automatic secret-redaction guarantee and no preview step: the selected evidence is transmitted as-is, so the user is responsible for choosing episodes acceptable to submit.
- **R3** — Ask two independent Jev Choice questions in one request. The first selects the intervention kind: `correction`, `clarification`, `requirement_change`, `decision_response`, `architecture_review`, or `insufficient_evidence`. Define correction as redirecting prior agent behavior/understanding, not proof of negligence or an ignored instruction. Distinguish changed requirements from a previously stated requirement the agent missed; use insufficient evidence when the supplied context cannot resolve the distinction. Mere words such as “no”, “still” or “revert”, and an agent's apology, are not sufficient grounds for correction.
- **R4** — The second Choice selects the primary observable issue: `abstraction_or_intent_mismatch`, `explicit_constraint_missed`, `unsupported_completion_claim`, `speculative_diagnosis`, `ownership_or_boundary_confusion`, `other`, `insufficient_evidence`, or `not_applicable`. Describe clear boundaries: an explicit-constraint miss requires prior evidence of that constraint; an unsupported completion claim asserts delivery without adequate support; speculative diagnosis concerns unverified causal explanations. Both questions judge the supplied evidence independently, not each other's answers. Preserve both raw answers; expose an effective issue only for a correction, otherwise `not_applicable`. Surface contradictory combinations for review rather than inventing a reconciliation.
- **R5** — Treat transcript contents as evidence, never as instructions to the classifier. Rubric criteria must preserve the pilot's negative cases: explicit removal followed by a request to restore, “no” accepting a recommended option, and an async constraint revised during design. Do not infer a historical rule from current preferences, equate disagreement with avoidable error, or treat later user approval as proof of a diagnosis.
- **R6** — Provide a proposed `episode classify <session.jsonl> --from <entry-id> --at <user-entry-id>` command that builds the request and submits it in the same invocation. Invalid input must fail before any network call. The command must not require an additional confirmation or opt-in flag; invoking it is the user's explicit request to submit. Existing bash commands must remain offline.
- **R7** — Only Jev may answer. Keep provider-specific endpoint, credential, model identifier and response mapping behind one internal provider interface with separate adapters, so a different Jev provider can be used without changing selection, projection, rubric or validation rules. Implement the direct TypeSafe provider and the OpenRouter provider. Each adapter pins its own versioned Jev model (no moving `latest` alias), reads only its own credential environment variable, and never accepts credentials as command arguments or repository files. Submit at most one request per invocation with a finite timeout; do not retry, follow redirects, or fetch additional evidence automatically. Do not expose credentials, request contents or raw provider error bodies in diagnostics.
- **R8** — Output is one JSON document with schema/rubric versions, provider identity, session/range/intervention identity, local source references, projection warnings, source-snapshot/request hashes, requested/returned model identifiers, returned labels, full probabilities, confidence, usage and elapsed request time. Validate answer types, option keys, finite values/ranges, probability totals within documented tolerance and selected choices against the maximum probability. Output no raw transcript or generated rationale. Treat all classifications as hypotheses requiring review; do not introduce an arbitrary automatic-accept threshold in this first version. Diagnostics use stderr; document fatal/invocation exit code 1 and successful classification exit code 0, with uncertainty represented in the JSON rather than as transport failure.
- **R9** — Read only the supplied session file; do not execute transcript commands, load agent extensions, migrate sessions, scan other sessions, modify source files or change instructions. Capture one read snapshot for consistent parsing/provenance; disclose that active files may grow between invocations. Write no report/cache automatically: users can redirect JSON into ignored `reports/`. Automated unit/integration tests use synthetic native-format JSONL fixtures and mocked transport, never credentials, paid calls or committed personal transcripts.
- **R10** — Verify the complete offline/HTTP contract and evaluate semantics separately. Synthetic native-format analogues of correction/control cases must exercise the rubric, branch selection, broken ancestry, repeated text with distinct IDs, projection warnings, payload boundaries, input/output validation, privacy, provider selection, timeout/failure paths and unchanged offline bash commands. Mocked answers prove plumbing, not Jev accuracy. Also validate end to end using a defined real Pi Chat session and selected episode: perform one explicitly enabled Jev call, compare the prediction with the manual review, record actual usage/disagreements privately, and verify the source was not modified. User approved real-session validation under Q2; that is not approval for a corpus-wide upload. The pilot episodes remain development examples, not a held-out benchmark. Do not claim calibrated confidence or population accuracy from this sample.

## Assumptions
- User confirmed native real-session input and real-session live validation, and explicitly declined a separate preview or network opt-in step.
- The user wants Jev only, not an alternative answering model, but expects to be able to change the Jev provider without reworking the feature. Provider adapters are therefore Jev-specific, not a general LLM abstraction.
- OpenRouter exposes Jev through a System One–compatible endpoint at base URL `https://openrouter.ai/api` (SDK path `/v1/systemone`) with `Authorization: Bearer <OPENROUTER_API_KEY>` and model slug `typesafe/jev-1.14`; an alpha Decisions endpoint also exists. The direct TypeSafe provider uses `POST https://api.typesafe.ai/v1/systemone`, `TYPESAFE_API_KEY` and `jev-1.14.0`. Confirm the selected OpenRouter endpoint and returned model format before the live trial.
- Use the archive-button episode E2 from the local pilot as the first defined real-session case: start entry `8fca4ad9`, intervention entry `c3365bde`. Resolve its private source path locally from the pilot evidence; do not copy that transcript into tracked fixtures. The existing private `reports/correction-review.json` identifies development cases and expected interpretations, **not** model input; its labels and interpretations must never be sent as evidence.
- Preserve Node 24+, TypeScript, small plain-function modules and the existing test tooling. A direct built-in HTTP client can keep the feature dependency-free; no agent framework or Python runtime is needed.
- Retention is governed by provider terms; lack of training on customer data is not a zero-retention guarantee. User authorized a selected real session for validation, not uploading all sessions.

## Implementation Plan
### S1 — Session Episode and Rubric
Description: Reuse native session parsing to select one ancestry-bounded episode, normalize its evidence and build the versioned two-question Jev payload (R1–R5). Verify supported JSONL versions, valid/invalid boundaries, sibling-branch exclusion, missing context, unsupported content, excluded annotations and size rejection using synthetic native-format fixtures. Preview the defined real-session episode locally to verify the real format before adding network access.

### S2 — Providers and Classification
Description: Build on S1 to expose the `episode classify` command, the provider interface with direct TypeSafe and OpenRouter adapters, and validated response handling (R6–R9). Verify that invalid input fails before any call, exactly one request is sent with the prepared bytes, provider selection and credentials resolve correctly, and valid probabilities/provenance are preserved. Use mocked transport only; no paid calls required to complete this slice.

### S3 — Real-Session Validation
Description: Build on S2 to validate the defined real Pi Chat session/episode end to end and add a short usage/evaluation guide (R10). Verify existing tests/typecheck and the synthetic native-format regressions. Submit one Jev request, and record label agreement/disagreement, usage, source integrity and projection coverage privately. If credentials are unavailable, report the live-validation blocker rather than substituting mock results as proof. Keep contract verification separate from semantic findings; do not expand into automatic boundary detection or recommendations.

## Open Questions
- **Q3** — How is the Jev provider selected for a run: an explicit `--provider` flag (recommended, so evidence cannot be silently routed to an unintended provider) or automatic detection from whichever provider credential is present in the environment?
- **Q1 — Resolved:** Use a real Pi session JSONL file directly, not manually curated episode JSON. Select the episode using explicit start/intervention entry IDs and derive its evidence internally, so the MVP exercises the actual persisted format.
- **Q2 — Resolved:** Use a defined real session for live validation, not only synthetic examples. Keep personal evidence private and limit submission to the selected episode; automated tests still use synthetic native-format fixtures.
