# Jev Episode Classification — Requirements

## Goal
Classify one explicitly selected conversation episode: is the user correcting the agent, clarifying, changing requirements, answering an open question, or initiating an architectural review? When it is a correction, identify the observable issue without claiming its root cause or preventability.

This is a feature-scoped proposal, not implementation approval. Preserve the existing root [requirements](../../REQUIREMENTS.md) as the legacy bash/metrics roadmap; do not relocate or rewrite it. Its offline-only constraint continues to apply to existing commands. This feature proposes a narrowly scoped, explicitly authorized network exception for the new command only.

Automatic episode discovery/extraction, session-wide scoring, recurrence analysis, recovery scoring, prevention recommendations, generated explanations, caching, dashboards, and automatic configuration changes are out of scope.

## Requirements
- **R1** — Accept one manually curated episode JSON file (subject to Q1). It contains an episode ID, a designated user-intervention message ID, ordered evidence messages/excerpts, local source references, and explicit context limitations. Unique message IDs and a valid user anchor are required. Include the original request and relevant prior agent behavior; subsequent messages may show recovery but cannot retroactively change the instructions that applied before the intervention. The tool does not discover episode boundaries or infer chronology from an arbitrary collection of quotes.
- **R2** — Keep evidence separate from interpretation. Model input contains conversation evidence and declared omissions, not the manual review's labels, observations, prevention hypotheses, or expected answers. Exclude hidden thinking and binary/image data. Curators select and sanitize excerpts; no automatic secret-redaction guarantee. Source paths and source-reference mappings remain local and are not needed in the provider payload. Reject malformed or oversized packets rather than silently trimming away context; document a conservative payload-size limit during implementation.
- **R3** — Ask two independent Jev Choice questions in one request. The first selects the intervention kind: `correction`, `clarification`, `requirement_change`, `decision_response`, `architecture_review`, or `insufficient_evidence`. Define correction as redirecting prior agent behavior/understanding, not proof of negligence or an ignored instruction. Distinguish changed requirements from a previously stated requirement the agent missed; use insufficient evidence when the supplied context cannot resolve the distinction. Mere words such as “no”, “still” or “revert”, and an agent's apology, are not sufficient grounds for correction.
- **R4** — The second Choice selects the primary observable issue: `abstraction_or_intent_mismatch`, `explicit_constraint_missed`, `unsupported_completion_claim`, `speculative_diagnosis`, `ownership_or_boundary_confusion`, `other`, `insufficient_evidence`, or `not_applicable`. Describe clear boundaries: an explicit-constraint miss requires prior evidence of that constraint; an unsupported completion claim asserts delivery without adequate support; speculative diagnosis concerns unverified causal explanations. Both questions judge the supplied evidence independently, not each other's answers. Preserve both raw answers; expose an effective issue only for a correction, otherwise `not_applicable`. Surface contradictory combinations for review rather than inventing a reconciliation.
- **R5** — Treat transcript contents as evidence, never as instructions to the classifier. Rubric criteria must preserve the pilot's negative cases: explicit removal followed by a request to restore, “no” accepting a recommended option, and an async constraint revised during design. Do not infer a historical rule from current preferences, equate disagreement with avoidable error, or treat later user approval as proof of a diagnosis.
- **R6** — Provide a proposed `episode classify <episode.json>` command that previews locally by default, with no API key or network required. Its JSON preview includes the exact provider request body, model, rubric version and payload size; it explicitly reveals sensitive evidence for review. Only an explicit `--allow-network` submits that payload. Preview and submission use the same request builder. An API key in the environment alone must not trigger a request, and existing bash commands must remain offline.
- **R7** — Submit at most one request per invocation using the TypeSafe API and an explicitly pinned model. Enforce a finite timeout; do not retry or fetch additional evidence automatically. Read the key from `TYPESAFE_API_KEY`, never a command argument or repository file. Do not expose it, request contents, or raw provider error bodies in diagnostics. Invalid input, missing credentials in live mode, timeouts, HTTP failures and invalid responses must fail clearly without fabricated classifications. Do not follow cross-origin redirects with credentials.
- **R8** — Live output is one JSON document with schema/rubric versions, episode/anchor identity, local source references, input/request hash, requested/returned model IDs, returned labels, full probabilities, confidence, usage and elapsed request time. Validate answer types, option keys, finite values/ranges, probability totals within documented tolerance and selected choices against the maximum probability. Output no raw transcript or generated rationale in live mode. Treat all classifications as hypotheses requiring review; do not introduce an arbitrary automatic-accept threshold in this first version. Preview and live output must be distinguishable. Diagnostics use stderr; document fatal/invocation exit code 1, successful preview/live exit code 0, with uncertainty represented in the JSON rather than as transport failure.
- **R9** — Read only the supplied episode file; do not execute transcript commands, load agent extensions, migrate sessions, modify source files or change instructions. Write no report/cache automatically: users can redirect JSON into ignored `reports/`. Unit/integration tests use synthetic data and mocked transport, never credentials, paid calls or committed personal transcripts.
- **R10** — Verify the complete offline/HTTP contract and evaluate semantics separately. Synthetic analogues of the reviewed correction and control cases must exercise the rubric, payload boundaries, input/output validation, privacy, timeout/failure paths, no-network preview and unchanged offline bash commands. Mocked answers prove plumbing, not Jev accuracy. After separate approval under Q2, compare live predictions with manually assigned expected labels, recording disagreements and actual usage; the ten pilot episodes are rubric-development examples, not a held-out benchmark. Do not claim calibrated confidence or population accuracy from this sample.

## Assumptions
- Start with curated evidence packets so episode extraction does not obscure whether the rubric works. The existing private `reports/correction-review.json` is an annotation source, **not** a valid model input; its labels and interpretations must never be sent as evidence.
- Proposed provider: direct TypeSafe `POST /v1/systemone`, pinned `jev-1.14.0`, currently documented in the [model catalogue](https://docs.typesafe.ai/models). Use the documented [Choice contract](https://docs.typesafe.ai/primitives/choice) and [API schema](https://docs.typesafe.ai/api/system-one); confirm availability before any approved live trial.
- Preserve Node 24+, TypeScript, small plain-function modules and the existing test tooling. A direct built-in HTTP client can keep the feature dependency-free; no agent framework or Python runtime is needed.
- Retention is governed by provider terms; lack of training on customer data is not a zero-retention guarantee. Planning or implementing this feature does not authorize transmitting personal episodes.

## Implementation Plan
### S1 — Episode Packet and Rubric
Description: Deliver the curated episode contract, validation, versioned two-question rubric and deterministic provider-payload builder (R1–R5), after resolving Q1. Use synthetic conversation examples, including the three control types, and keep expected labels separate from model input. Verify malformed anchors, explicit missing context, chronology, excluded annotations and size rejection without any network access.

### S2 — Preview and Jev Classification
Description: Build on S1 to expose the new preview-first CLI and one-request TypeSafe integration (R6–R9). Verify that preview needs no credentials/network, live mode requires explicit permission, submitted content matches preview, valid probabilities/provenance are preserved, and HTTP/timeout/schema failures cannot produce success. Preserve all existing bash CLI behavior. Use mocked transport only; no paid calls required to complete this slice.

### S3 — Development-Case Validation
Description: Build on S2 to add end-to-end regression cases and a short usage/evaluation guide (R10). Verify existing tests/typecheck plus the new fixture cases. Resolve Q2 before any live trial; record live label disagreements, usage and coverage privately if authorized. Keep mock-contract verification separate from semantic findings; do not expand into automatic extraction or recommendations.

## Open Questions

- **Q2** — For the first live validation, should we send synthetic examples only (recommended), or may we submit explicitly reviewed Pi Chat excerpts?
